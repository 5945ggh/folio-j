# Folio-J 后续讨论备忘：学习行为、词汇身份与材料预处理

## 1. 用户提出的学习行为与证据方向

用户希望未来能记录或查询以下信息，并认为它们可能支持学习逻辑与推荐：

| 用户提出的内容 | 暂存含义 |
| --- | --- |
| 跨来源、跨材料，全局第一次阅读到某个 lexeme | 不仅看单本书，还能在所有学习输入中认识接触历史 |
| 即时查词查到某个词条 | 留下查词行为与词条关系；即时查词本身尚未排期 |
| Segment 中出现的 lexeme | 让片段学习与词汇出现情况建立可用联系 |
| 用户主动标记材料已完成 | 既能服务当前素材管理，也可能成为后续可回顾的行为 |

以上是方向，不是“见过即掌握”“查过即不会”的学习判据；目前没有给出推荐策略、合格接触标准、全局首次的可观测范围或保留周期。

### 1.1 讨论建议：先区分四种东西

| 类别 | 例子 | 不能据此直接推出什么 |
| --- | --- | --- |
| 内容事实／派生关系 | 某版本材料或 Segment 的某个范围被切成一个 token，并关联某词汇候选 | 不证明用户实际看过这段内容 |
| 可观察交互 | 打开材料、一次查词请求、选择某词条、手动标记完成 | 不自动证明理解、记住或掌握 |
| 当前状态 | 最后阅读位置、最后打开时间、当前完成状态 | 不等于保留了完整事件历史 |
| 规则派生的学习证据 | 按给定接触判据得到的首次记录、频次、间隔 | 结论依赖观测范围与判据，不是未经限定的现实事实 |

例如，“Segment 中出现的 lexeme”首先是内容关系，可以由解析结果派生；“用户在一次学习中打开这个 Segment”才是一个动作。首次接触则可能是多个合格观察的聚合结果，不一定必须有一张永远不可修正的“首次接触事件”表。

系统通常只能说“在当前被记录的范围内首次观察到”，不能宣称用户人生中第一次遇到这个词。预加载整章、滚动经过或隐藏标签页中的文字，不应在没有明确判据时全部计作已经阅读。后续需要分别讨论用户行为、应用可观察信号和推断规则。

当前快照并非完全没有记录：存在 ReadingPosition、ChatMessage、Job／Run 等状态和执行资料；缺的是统一服务于上述学习证据的设计。最近打开和三态管理只先交付必要当前状态，不为了“以后可能有用”全面收集所有 UI 事件。

**已有实现依据：** `backend/src/app/material_models.py`、`chat_models.py`、`settings_models.py`；实际采用字段以届时本地代码为准。

### 1.2 后续值得收口的少量问题

接触记录应能保留观察对象的材料／正文版本与位置、观察时间、触发方式和判据版本；具体最小字段留待一个可运行场景决定。分析规则可以变化，但不能让升级分词器悄悄把旧行为改成另一种行为，或者把同一次接触重复累计。

查词需要区分查询文字、所处语境、展示候选与用户实际选择的词条。一次查询可能得到多个词条，词典条目身份也不必与我们的 lexeme 身份相同。“查到了列表”与“确实点开其中一个解释”应按实际能够观察的事实记录。

用户的手工完成标记属于明确动作；“当前 completed”是该动作带来的当前状态。本轮可以只保存状态，未来确实需要历史时，再加入相应事件，不宣称此前每次状态变化都能从当前值完整复原。

学习证据先本地保存，优先记录有解释价值的信号，不默认上传用户阅读／查词历史。不从界面状态自动推断用户的能力等级或心理状态。

## 2. Lexeme：保存用户的候选定义，但暂不冻结身份规则

### 2.1 用户的原始提案

用户提出：lexeme 也许可定义为 Sudachi 切词后的 `(surface, POS, canonical form)` 三元组，身份中不包含切词器版本。这里将原消息中 `canocical` 按通常拼写记为 `canonical`，但其具体字段含义仍未确定。

“不把切词器版本放入领域身份”是值得保留的目标：不希望仅因软件升级，就把既有学习对象全部当成从未见过的新词。但这不等于可以完全不保留分词与词典的处理来源。

### 2.2 核实到的工具事实

SudachiPy 官方 API 分别提供 `dictionary_form()` 与 `normalized_form()`；二者不是一个笼统的 `canonical_form()`。`part_of_speech()` 返回六个分量，除四级词性外还有活用类型和活用形。官方也提供 `raw_surface()`，以避免配置的 surface projection 混入“原文形式”的含义。README 明示示例输出可能随词典版本变化。

**官方依据，查阅于 2026-10-04：**

- `https://worksapplications.github.io/sudachi.rs/python/api/sudachipy.html`
- `https://github.com/WorksApplications/sudachi.rs/blob/develop/python/README.md`

这些事实只用于澄清候选定义，不等于 Folio-J 现在已经安装相应版本，也不是本轮升级依赖的要求。

### 2.3 讨论建议

若把原文 surface 也纳入身份，不同实际词形会天然成为不同键；若 POS 使用全部六个分量，活用差异还可能继续区分它们。因此，这个三元组可以作为某种细粒度词形索引候选，但是否应直接称为最终 lexeme，要看我们希望学习历史按“实际形式”“词典形式”还是更具体的用法聚合。

反过来，移除 surface、只取规范形也不自动解决同形异义、词典条目差异或切分粒度问题。不要现在就给出一个据称永远正确的更短元组替代它。

建议分开讨论：一次具体 token 出现、词形表示、跨出现聚合的词汇身份、词典条目及以后知识点之间的关系。版本可以不进入最终 lexeme ID，但输入正文、处理器／词典版本、切分模式、规范化配置应进入派生结果的来源记录。领域身份规则自身若调整，需要明确如何关联旧身份，不能静默重写历史。

**已有仓库边界：** [材料定位方案第 8 节](../epub-reading/MATERIAL_BASELINE.md#8-分词与派生数据的后续接入)已经区分 token 与候选 lexeme 归并信息，并要求 sidecar 记录处理来源；分词不改变定位正文、材料版本或已有引用。保留这些边界，不把讨论中的新三元组自动写进 GLOSSARY 的“已确认”定义。

## 3. 音视频、外部目录与字幕

### 3.1 用户提出的方向

视频等大文件优先通过添加文件夹发现和引用，原文件留在外部位置，不复制一整份大文件到应用存储。用户进一步提出：视频／音频作为学习材料，应绑定 `.ass` 等字幕文件，字幕应不可变。

文件夹只负责内容接入与位置发现，不等同于 Source。停止扫描、移除材料记录、删除磁盘原文件，以及删除学习成果必须分别考虑。默认不修改／删除外部媒体文件。素材库的类型／Source 组织不必复制物理目录树。

### 3.2 讨论建议：把“不可变”落在已发布的字幕版本上

可以保存一份小而确定的字幕输入副本或等价的受托管字节，并记录摘要和来源。学习位置与派生正文关联到这份确定版本，而不是仅保存一个将来可能被其他软件改写的 `.ass` 路径。

以后用户修正错字、替换字幕或调整时间，不必被禁止；应当以新字幕版本或明确的对齐配置表达变化，历史引用仍保留原依据。绑定关系除了字幕文本版本，还需要说明它对应哪个媒体版本／轨道，以及按什么时间对齐，避免“文字没变”却已经跳到另一段声音。

这是建议，尚未决定所有字段、时间单位、字幕格式范围或迁移方式。也不要求为了保证字幕快照，重新复制整部视频。

“作为学习材料须有字幕”与“扫描时发现了没有字幕的文件”是两件事。后续应明确无字幕条目的呈现、绑定流程以及是否允许纯播放；不能在没有讨论时自动加入 ASR、网络下载字幕或放宽用户提出的学习前提。

## 4. 跨素材预处理结果的共同抽象

### 4.1 用户提出的方向

不同类型素材的预处理过程可以千差万别，但处理结果也许可以在一定程度上统一，让正式学习功能使用共同接口。用户认为应先建立这种抽象，再通过真实使用修订，不必等待完美方案。

### 4.2 讨论建议：先统一学习侧需要的契约，不强制相同内部表示

值得最先抽象的是这类问题：这份材料的稳定身份和版本是什么；有哪些可寻址内容；怎样取得指定目标文本及语境；怎样把保存的出处定位回阅读／播放环境；哪些能力当前可用。

这可以用薄接口、协议或能力组合表达，不一定必须是深继承树。共同契约可以存在，不代表 EPUB 章节、字幕片段和图片区域必须变成同一种“句子”记录。

| 共同问题 | 允许按类型保留的差异 |
| --- | --- |
| 材料与版本身份 | 原始输入可以是托管 EPUB、外部视频引用配字幕快照等不同组合 |
| 可引用的内容 | 资源内文本范围、确定字幕记录的文本范围、图片中的区域等可以具有不同坐标类型 |
| 阅读／播放定位 | 书内位置、媒体时间和页面区域不必强行换算成同一种全局偏移 |
| 可取目标与语境 | 文本、字幕、图片派生文本等能力应明确支持与限制，不用大量静默空值伪装统一 |
| 显示与派生数据 | 封面、分词、注音、缩略图或未来 OCR 等可以各自重建，不当然改变原文身份 |

未来设计可用“EPUB 阅读范围”和“一段已绑定字幕的视频”两个最小实例来检验同一接口：由学习侧调用共同能力，由媒体适配器处理不同位置与呈现。尚未支持的第三类材料可以保留边界，不为它提前实现整套管线。

需要避免的过早定型包括：把正文等同于屏幕排版后的 `innerText`；假设所有材料都有互不重叠的一维连续段落；把词汇 token 编号当永久出处；把自动派生结果与用户原始输入放进同一个不可区分的版本；给所有媒体设置一长列多数为 null 的字段。

此处支持“先形成一个可检验的薄契约”，但不把它加入当前前端验收依赖。前端只需要可读的目录摘要、材料身份和明确可进入的阅读界面；不应趁类型 tabs 重构，就从一个 EPUB 实现推导并上线完整通用预处理基类。

## 5. 后续讨论的建议落点

前端可实际体验后，先拿一个带确定字幕的音视频学习场景检验“预处理结果共同契约”；再用一个明确的接触／查词场景区分原始事件、内容关系与可重算学习证据。Lexeme 身份服务于这些问题，不必在没有用例的情况下先求一个万能三元组。

本备忘只保证这些想法被记录下来，不要求它们改变已确认的“前端调整→独立全量注音→选区学习”的近期执行顺序。若后续决定改序，应明确更新阶段安排。
