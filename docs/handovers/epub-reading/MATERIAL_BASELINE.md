# EPUB 材料与定位主要设计方案

> 设计形成于 2026-10-03，依据 LearningJ 只读调查与官方标准。本文维护材料身份与定位方案，交付状态及验收入口见 [MVP 实施基线](../MVP_IMPLEMENTATION_BASELINE.md)。
> 本文维护材料身份与定位设计；存储、API 和删除规则见[切片 1 契约](SLICE_1_DRAFT.md)，产品动机见[方向讨论稿](DIRECTION.md)。

首轮以普通可重排 EPUB 为对象，建立可靠的材料身份、原文引用与阅读位置关系。借鉴 LearningJ 的身份分离、位置转换与校验、针对性测试；不整套迁移其阅读器和 Unicode 字素簇实现。素材到材料的可逆映射不是要求。

## 1 本轮选定的主要做法

| 问题 | 首轮方案 | 取舍理由 |
| --- | --- | --- |
| 原始素材怎样保留 | 导入时托管原 EPUB 的不可变副本，记录字节摘要；首轮不做仅引用外部文件路径的模式 | 书被移动或外部修改时，历史引用仍有确定依据 |
| 材料是什么 | 材料有稳定身份，属于一个 Source；保存元数据和指向原始素材及处理版本的关系 | 来源、文件内容、处理结果各自有明确职责 |
| 处理结果怎样变化 | 导入结果带不可变版本身份；首轮不做重新处理入口或版本管理 UI | 先保证历史引用有确定依据，不提前建设版本管理产品 |
| 位置记在哪里 | 具体材料版本中的原始 spine 资源，加该资源定位正文的 Unicode 码点范围 | 不受界面章节分组、翻页、字号或窗口尺寸影响 |
| 如何校验引用 | 保存半开范围及原文快照，读取和保存时核对资源与文本 | 重复文字可由位置区分，失配可识别 |
| EPUB CFI 怎样使用 | 作为阅读器适配或互操作的可选信息，不作为应用唯一的引用依据 | CFI 与应用正文使用不同坐标，且仍依赖出版物结构 |
| Unicode 怎样处理 | NFC 用标准运行时能力；交互边界优先使用浏览器能力；持久坐标统一为码点 | 避免自行维护完整多语言属性表和两套字素簇算法 |
| 如何接入学习 | 消息保存原文引用，Segment 可带材料出处，Analysis 沿用已有归属 | 轻问答不必先创建 Segment，也不另建一套讲解模型 |

阅读引擎、CSS 保留范围和基础呈现已在切片 0／1 落实。消息引用和学习衔接按后续切片实施。

## 2 材料身份与版本

区分四层信息，但不要求它们立即对应四张表：

| 层次 | 保存的依据 | 哪些变化不改变它 |
| --- | --- | --- |
| 原始素材 | 原 EPUB 字节及其摘要 | 文件显示名称变化 |
| 材料 | 稳定 ID、所属 Source、用户管理信息、原始素材关系 | 标题修改、阅读进度变化 |
| 材料版本 | 处理契约版本、定位及呈现所需的核心产物与校验信息 | 字号、主题、阅读位置，以及可选分词结果变化 |
| 版本内资源 | 原始 spine 项身份、规范化资源路径、定位正文与其摘要 | 多个资源合并成一个界面章节 |

原始字节摘要用于核对输入，不用书名或文件名推断“同一本书”。首轮按一份材料归属一个 Source 设计，不据此承诺永远不支持共享关系。同一 Source 下重复导入完全相同字节时，优先返回已有材料；同一字节出现在不同 Source 时不合并领域记录。物理文件是否复用可独立处理，不预建共享材料库。内容不同的文件首轮作为新材料处理，不自动当成原材料的升级版本。

版本同时记录处理规则和实际产物，不能只靠一个“解析器版本号”猜测内容是否相同。章节显示分组属于呈现组织，持久位置始终落在版本内资源上。首轮只需导入产生确定版本，并将引用绑定到它；不要求版本切换界面、重新处理入口或自动清理功能。打开书或升级应用不悄悄改变已发布的版本内容。

以后若增加显式重新处理，应生成新版本并保留旧引用的依据；届时再设计当前版本入口与版本差异呈现。打开历史引用使用其绑定的版本。如果对应版本不可用，保留可阅读的引用快照并说明无法定位，不把旧偏移直接套在另一版本上。

当前材料随 Source 删除而不可见，托管原始字节与编译产物暂保留在数据库中；独立材料移除留待后续。来源下的学习内容按 [PRD F2](../../PRD.md#f2-source-与片段)级联删除，具体存储与门禁见[切片 1 契约](SLICE_1_DRAFT.md)。

## 3 定位正文与阅读呈现

每个版本内资源保存一份确定的“定位正文”，作为选区、引用、语境提取的文本坐标依据。它是从内容结构提取的正文，不以随排版变化的 `innerText`、显示页码或屏幕像素为依据。

首轮采用这些应用规则：

- 解析标记并解码文本实体，统一换行形式，对定位正文作 NFC；原 EPUB 字节保持原样。
- ruby 的 base text 进入定位正文，`rt`、`rp` 等注音与回退文字不进入正文偏移；读音信息按需单独表达。
- 脚本、样式文本和应用注入的按钮、标记等不进入定位正文；不使用 NFKC 改写作为出处的正文。
- 块间分隔与隐藏内容的处理规则须确定、带版本，并在导入端和阅读适配器中一致；具体规则通过 EPUB 样例固定，不能随当前 CSS 排版临时变化。

这些规则属于材料的文本投影，不改变 Analysis 规范化器现有的可复原、不改写契约。

阅读器可以保留适用的结构、CSS、图片和 ruby 呈现，也可以采用受控布局；定位契约不绑定 ShadowRoot 或某一引擎。外部内容的执行隔离、资源访问与清洗范围在渲染方案中验证，不能仅以“正文出现在 ShadowRoot 中”当作隔离保证。

用户已确认按书内目录组织阅读章节及原目录章名，图文分散于多个 spine 项时仍应连续阅读。目录提供导航入口和层级，spine 提供资源阅读顺序；逻辑章节使用有序资源范围表达，可跨资源，也可能在同一资源的 fragment 处分界。缺失、逆序或不完整的目录需要显式回退，不能承诺出版物本身没有表达的语义章边界。组章不会重写各资源正文或引用坐标，具体实施与恢复见[切片 1 草图](SLICE_1_DRAFT.md)。

阅读进度以逻辑章呈现，以版本、资源及正文位置恢复；章内百分比是辅助显示，不作为唯一位置。纯图片处使用受控资源内的图片位置及局部比例。字号／行距／横竖排变化后允许恢复到原附近；此近似容错仅限阅读进度，不降低原文引用的精确校验要求。

定位适配器负责两次转换：浏览器选区到版本内资源范围，以及已保存范围到可显示的选区。阅读 DOM 的文本投影必须与已保存正文一致；不一致时拒绝创建声称精确定位的引用，保留普通阅读或无定位提问的能力。

## 4 原文引用的最小信息

一条消息可有零个或多个原文引用。引用记录具体材料版本以及有序的资源局部范围，每个范围包含：

| 信息 | 用途 |
| --- | --- |
| 版本内资源身份 | 确定是在原 EPUB 的哪一个内容资源中 |
| `start` 与 `end` | 零起点、Unicode 码点、`[start, end)` 半开范围 |
| `exact` | 当时被引用的定位正文，保存时须等于对应区间切片 |
| `prefix` 与 `suffix` | 限长的邻近文字，辅助人工识别和以后可能的恢复；不作为独立学习语境 |

材料版本保存了正文摘要，引用通过版本和资源关系使用该校验信息，不必把整套资源元数据复制到每条消息。展示摘录可按需要拼接，但不把跨资源选区伪装成一个全书偏移范围。

问题焦点、模型需要的语境和最终 Segment 范围分别表达。发送请求时固定本轮引用、实际语境与版本；之后继续翻页或修改输入框中的选择，不改变已接受的请求。语境窗口及默认自动带入规则仍待阅读问答设计确定。

本方案借鉴 Web Annotation 的位置和文本引用思路，采用应用自己的数据契约，不宣称实现了完整 W3C Annotation 格式。EPUB CFI、DOM Range 或元素路径如有使用，留在阅读器适配边界，不能直接与码点偏移互换。[Web Annotation](https://www.w3.org/TR/annotation-model/#selectors)、[EPUB CFI](https://w3c.github.io/epub-specs/epub33/epubcfi/)

## 5 Unicode 的精简边界

LearningJ 的大文件实际是 Unicode 15.1 字素簇属性表：前后端各约两千行，另有生成器与上游测试数据。NFC 本身已经使用 Python `unicodedata.normalize` 与 JavaScript `String.normalize`，并没有自制的 NFC 合成分解库。字素簇边界用于避免选区切开组合字符或 emoji，和 NFC 是不同问题。

本轮保留标准 NFC、码点范围、浏览器 UTF-16 边界转换、ruby 排除与正文一致性校验。默认沿用浏览器原生选区；需要额外的交互边界修整时，优先采用目标浏览器支持的 `Intl.Segmenter`。缺少该能力时不自行按 UTF-16 单元截断字符，可先保留原生选区，不提供额外吸附。

不迁移完整 EGC 属性表、双端 UAX #29 自实现和全部 Unicode 测试语料，也不通过删除非日语字符来降低复杂度。后端验证资源、范围、码点边界和原文切片，不以两端实现同一版本的完整 EGC 算法作为入库前提。字素簇编号不进入持久坐标。

仍需保留真正必要的转换：DOM Text 和 `Intl.Segmenter` 的索引使用 UTF-16；持久范围使用码点；跨 DOM 节点的 NFC 组合还可能改变长度。不能逐节点取长度后相加，就声称得到可靠的规范正文坐标。首轮根据实际阅读 DOM 实现最小映射，遇到不能验证的范围明确失败，不盲目复制旧项目全部候选边界恢复逻辑。[ECMA normalize](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype.normalize)、[ECMA Segmenter](https://tc39.es/ecma402/#sec-findboundary)

浏览器分段实现和 Unicode 数据版本可能不同。固定入库正文并核对实际投影，避免将差异转化为错误的位置；记录处理环境供排查，不据此承诺所有运行时对任意新字符都产生相同结果。[UAX 15](https://www.unicode.org/reports/tr15/)、[UAX 29](https://www.unicode.org/reports/tr29/)

## 6 解析位置与形成成果

首轮只提供精确版本定位。版本、资源、范围及快照全部吻合，才绘制原文标记；失配或材料不可用时保留历史文字，显示无法定位的状态。不静默在全书搜索相同文字并迁移引用，也不先实现模糊恢复算法。

精确相同范围可以聚合显示一个讨论标记，但保留各条消息与引用的身份。重合范围不自动合并；具体分层、选择和显示方式留在交互设计。标记由引用派生，不单独保存一份箭头或侧边书签状态。

阅读对话的目标是材料，片段对话的目标是 Segment。复用线程和消息基础，并明确每条线程的归属类型；不依靠任意填写某个 `segment_id` 来容纳材料对话。接口、权限与 Job 输入快照的扩展需另作实施契约，当前代码不因此获得材料读取能力。

从原文建立 Segment 时复制选定目标文本，并保存可选的精确材料出处；从讨论整理讲解时再选定目标范围和相关问答，调用已有 Analysis 能力。原文引用与 Segment 出处可以共用定位格式，但各自保留关系。默认不按相同文字自动合并 Segment；已有同处片段可供显式选用。手动录入与无定位提问仍可成立。

例如，一条问题同时引用 A、B 两处作比较，用户随后只要求整理 A 的讲解，则以用户确定的 A 为 Segment 目标，B 可作为语境或比较依据。不能把所有消息引用自动拼成目标原文，也不迁移整条阅读线程；Analysis 继续归属选定的 Segment。

## 7 迁移与验证重点

先验证定位与基础阅读，随后从原文接入已有 Segment 与工作台，再加入材料对话、消息引用和从讨论整理讲解。这样可以先验证已有学习能力与阅读器的衔接，再扩展线程范围；具体顺序与验收见[阶段入口](README.md)。迁移以小范围提取实现和测试为主，不整体搬入旧的文件编译器、渲染组件或 Unicode 子系统。

首轮针对性案例至少覆盖：

- 日文浊点组合与预组合形式、跨节点 NFC、代理对字符及常见 emoji；确认 UTF-16 和码点未混用。
- ruby、实体、换行和块间分隔；确认导入正文、选择摘录和反向显示一致。
- 重复文字、重合引用、跨节点和已加载资源间的选区；未支持的跨章节选择明确表达。
- 字号、窗口和阅读布局变化，以及 UI 章节分组变化；引用仍落在同一版本资源和文字上。
- 原文快照失配、版本不同、资源不可用；不误画标记、不覆盖旧引用。
- 引用附着到消息、消息定位、创建 Segment 后的出处与 Analysis 归属；能走通保存后的重新打开流程。

切片 0 的定位与浏览器验证见[独立记录](SLICE_0_ACCEPTANCE.md)，切片 1 的导入、持久化与阅读恢复见[验收记录](SLICE_1_ACCEPTANCE.md)。消息引用、从材料创建 Segment 及其学习成果的保存重开在后续切片验证。LearningJ 调查未迁移其数据库或运行其完整测试；首轮采用上述针对性 Unicode 案例。

## 8 分词与派生数据的后续接入

SudachiPy + SudachiDict-core、A 粒度已经列于 [TECH_STACK](../../TECH_STACK.md)，当前仍为预留、未安装。等词级选取、查词辅助或统计等具体需求出现后，可为已有材料补算分词结果，不要求用户重新导入，也不把分词放入首轮阅读的关键路径。

派生结果以 sidecar 的方式附着于具体材料版本与资源正文；这里的 sidecar 表示逻辑上的伴随数据，不预定必须是独立文件或某种通用存储框架。接入时记录输入正文摘要、分析器与词典版本、切分模式、分段及相关配置、结果契约版本。分词数据缺失、失败或失效，不影响基本阅读、引用定位和已有讲解。

现在要保留的边界是：

- 材料定位正文及其身份不由分词结果决定。对同一正文重跑或升级分词，只产生新的派生结果；不改原文、材料核心版本或旧引用。
- token 表达正文某个位置的一次切分结果；词典形、规范形及候选 lexeme 归并信息表达语言分析结果。两者分开，不把 token 序号、词典内部 ID 或规范形直接用作永久的原文位置身份。
- 分词以确定的正文为输入，结果位置转换并校验到相同的资源码点坐标。若内部规范化或分段处理改变字符串长度，必须显式对齐，不能用规范形长度或逐词搜索反推位置。
- 原文引用可以跨越 token 边界，分词失败或粒度变化不改变已有选区；HTML 中新增词级包装也不应改变定位正文。
- 后补振假名同样作为派生显示数据，绑定版本／资源的原文范围。原书 ruby 优先：自动候选只要与原书注音覆盖范围重叠就不直接覆盖或叠加；跨越原书 ruby 的 token 不能据此拆毁原书标记，无法可靠细分时跳过该候选。
- 渲染区分原书注音和自动注音，后者可以重算或关闭。所有 `rt`／`rp` 仍排除于定位正文；自动注音的开启／关闭及 token 包装不得改变正文叶子身份和码点映射。当前试验适配器限制叶子内部结构，接入 token 级包装时须扩展适配与回归测试，不能把目前的拒绝边界误称为已支持任意嵌套。
- 首轮保留稳定正文、版本、资源身份和可靠偏移即可，不预建 Lexeme 表、tokens 字段、调度器或 sidecar API。

LearningJ 的 EPUB 导入支持先不生成 sidecar，后续从已保存的规范 Sentence 文本独立重建；token 与跨出现位置的 Lexeme 是不同对象。Folio-J 可借鉴这种独立派生的边界，不必继承其 Sentence、词频索引、MessagePack 存储或词汇身份规则。

Sudachi 官方文档分别提供 surface、dictionary form、normalized form 等结果，并说明词典版本可能影响输出；其规范形转换不能代替出处正文。LearningJ 当前 sidecar 保存 normalized form，不应将它误称为 dictionary form。接入时复核当前 API 与版本。[SudachiPy 当前官方文档](https://github.com/WorksApplications/sudachi.rs/tree/develop/python)

## 9 依据及仍需讨论的内容

LearningJ 调查支持借鉴身份分离、版本化正文、DOM 到码点的转换、严格校验与测试；调查也发现原 CSS 被剥离、定位适配器尚未接成完整进度与标注保存流程。旧代码存在不等于已验证可直接迁移。

官方资料查阅于 2026-10-03：

- [Web Annotation Text Position](https://www.w3.org/TR/annotation-model/#text-position-selector)与[Text Quote](https://www.w3.org/TR/annotation-model/#text-quote-selector)：支持码点半开范围与文本快照的设计依据，并提示资源修改造成的位置脆弱性；没有替应用规定 NFC、ruby 或块间分隔规则。
- [EPUB 3.3 spine](https://www.w3.org/TR/epub-33/#sec-spine-elem)与[布局](https://www.w3.org/TR/epub-33/#layout)：区分内容资源顺序与阅读系统的动态分页。
- [EPUB CFI 1.1](https://w3c.github.io/epub-specs/epub33/epubcfi/)：定义结构路径、UTF-16 文本偏移和文本断言，不提供跨任意内容变化的永久身份保证。
